# SpeakSpace Local 本地大语言模型 / 小语言模型第二轮评估报告

## 摘要

本轮测试了 4 个面向 16GB 桌面设备的新候选模型：

1. `gemma4:12b-it-qat`
2. `qwen3:8b-q4_K_M`
3. `gpt-oss:20b`
4. `granite4.1:8b-q4_K_M`

4 个模型都能在 Apple M4 / 16GB RAM 的 Mac mini 上通过 Ollama 启动并完成至少一轮本地调用。综合加载速度、任务延迟、结构化输出稳定性和人工复核质量，`granite4.1:8b-q4_K_M` 是本轮最值得继续测试的 16GB 新候选。它不是最快的历史模型，但在本轮 4 个新模型里最稳，英文、中文、印地语、JSON 和忠实问答都完成了任务。

`qwen3:8b-q4_K_M` 的英文、JSON 和忠实问答表现好，但中文和印地语任务在 `num_predict=650` 下出现输出截断，疑似默认思考 / 生成策略消耗了较多输出预算。它值得继续测，但下一轮应加入更强的“简短输出 / no thinking”提示词或换 instruct 标签验证。

`gpt-oss:20b` 的质量整体可用，JSON 和忠实问答正确，但在 16GB 设备上的速度太慢，平均单任务约 6 分钟，不适合作为 V1 默认桌面模型。它更适合作为高质量离线参考模型或 32GB 设备上的补充测试对象。

`gemma4:12b-it-qat` 在本测试参数下不建议继续作为 16GB 主候选：英文、中文和忠实问答均出现截断，混合 JSON 任务返回空内容，结构化输出风险较高。

> 证据：
> - 来源：本轮本地测试结果，运行编号 `20260611-204938`
> - 方法：4 个模型各跑 5 个固定任务；通过 Ollama 本地 `/api/chat` 非流式调用；每个模型测试完成后执行 `ollama stop` 和 `ollama rm`
> - 置信度：中等。该测试是单设备、单轮小样本测试，适合做 16GB 桌面端候选筛选，不等同于最终生产基准。

人工复核重点：

- `gemma4:12b-it-qat` 在多个任务中达到 `num_predict=650` 的生成上限，英文、中文和忠实问答输出都在句中截断。混合 JSON 任务最终内容为空，JSON 校验失败。
- `qwen3:8b-q4_K_M` 的英文任务完整，JSON 可解析，忠实问答正确。但中文任务在模型列表处截断，印地语任务在行动项处截断。它的任务内容方向正确，但在当前提示词和生成上限下不够稳。
- `gpt-oss:20b` 的输出质量整体好，中文、JSON 和忠实问答尤其稳定。主要问题是速度：平均单任务约 361 秒，预热加载约 81 秒，不适合默认交互路径。
- `granite4.1:8b-q4_K_M` 的输出最均衡，5 个任务都完成。忠实问答第 4 题回答为 `Not mentioned (the cloud vendor is not specified in the transcript).`，语义正确，但没有严格按提示词输出小写的 `not mentioned`。
- 本轮所有模型都在测试完成后成功删除，最终 `ollama list` 为空。

## 推荐结论

| 排名 | 模型 | 建议 |
|---:|---|---|
| 1 | `granite4.1:8b-q4_K_M` | 本轮最值得继续测试的 16GB 新候选。速度、加载、JSON 和多语言任务完成度最均衡。建议进入下一轮真实 STT 输出测试。 |
| 2 | `qwen3:8b-q4_K_M` | 值得保留，但不能直接按本轮配置作为默认模型。下一轮应测试更短提示词、`/no_think` 或 instruct 变体，重点解决中文和印地语截断。 |
| 3 | `gpt-oss:20b` | 质量可用，但 16GB 上太慢。不建议作为默认模型，可作为高质量离线参考模型或交给 32GB 设备继续测。 |
| 4 | `gemma4:12b-it-qat` | 本轮配置下结构化输出和截断问题明显，不建议继续作为 16GB 主候选。 |

和第一轮已测模型对比，本轮还不能直接推翻 `Qwen2.5-3B-Instruct` 作为 V1 默认候选的结论。`granite4.1:8b-q4_K_M` 是最有价值的新挑战模型，但它的平均延迟仍明显高于第一轮的 `Qwen2.5-3B-Instruct`。如果 V1 优先级是低延迟和低资源占用，应继续保留 `Qwen2.5-3B-Instruct`；如果 V1 更看重结构化输出和多语言稳健性，建议让 `granite4.1:8b-q4_K_M` 进入真实转写文本复测。

建议项目下一步：

1. 将 `granite4.1:8b-q4_K_M` 加入第二阶段真实 STT 输出测试。
2. 对 `qwen3:8b-q4_K_M` 单独做一次短输出 / no-thinking 配置复测，确认截断是否只是提示词和生成预算问题。
3. 不把 `gpt-oss:20b` 放入 16GB 默认模型路径；如需继续验证，交给 32GB 设备或只作为离线质量参考。
4. 暂停 `gemma4:12b-it-qat` 的 16GB 主线测试，除非后续有更明确的 Ollama 标签、提示词或参数能解决空 JSON 和截断。
5. 应用侧继续保留 JSON 校验、代码块剥离和失败重试逻辑，因为不同模型对结构化输出的遵循程度仍不一致。

## 测试方法

本轮通过临时 Python 脚本调用 Ollama 本地 HTTP 接口完成。每个模型的流程为：

1. `ollama pull`
2. 预热调用
3. 依次执行 5 个固定任务
4. 记录 `ollama ps`、任务延迟、输出速度、自动校验和人工复核结论
5. `ollama stop`
6. `ollama rm`

自动检查覆盖：

- 响应是否为空
- 关键事实锚点是否保留
- 输出文字系统是否大致匹配任务语言
- JSON 是否可解析

最终排序主要参考人工复核，因为自动检查不能完整捕捉截断、冗余推理、提示词不严格遵循、轻微语言错误和交互延迟问题。

按照清理要求，测试脚本、原始输出和 JSON 结果文件在报告整理完成后删除；本文保留关键配置、性能指标、质量复核结论和推荐顺序。

## 局限性

- 只测试了一台设备：Apple M4 / 16GB RAM。
- 每个模型每个任务只跑了一次，没有测延迟方差。
- 测试文本是受控的会议转写风格文本，不是真实 STT 输出，也没有包含识别错误。
- `num_predict=650` 与第一轮报告保持一致，但对默认会输出较多思考内容或冗长答案的模型不友好。
- 印地语质量只做了明显任务完成问题的人工复核，没有由母语审阅者做专业语言评分。
- 首次模型下载耗时受网络条件影响，本报告不把下载速度作为模型质量结论。
